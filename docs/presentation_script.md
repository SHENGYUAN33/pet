> 每段標了預估時間；若只有 10 分鐘，講【★】標記的段落即可。

## 【★】開場（40 秒）

> 「今天跟您報告的是『貓狗寵物 30 秒領養廣告生成系統』。
>
> 一句話定義：**收容所把一隻待領養寵物的照片、影片和健康紀錄丟進來，系統自動產出一支帶旁白、字幕、配樂的 30 秒直式短影音，經過人工審核後可以直接發到 TikTok、IG、YouTube Shorts。**
>
> 我想先澄清一件事，因為它決定了整個技術架構的長相 —— **這不是一個「文字轉影片」的工具**。市面上那類工具輸入一段文案、輸出一支影片，我們刻意沒有走那條路。原因我用三分鐘說明，因為它是整個設計邏輯的起點。
>
> 今天我會講四塊：**設計邏輯、技術架構、目前實作到哪裡、實測結果**，最後有幾個問題想請教您。」

## 【★】一、設計邏輯：為什麼不是「文字轉影片工具」（3 分鐘）

> 「如果我們做的是文字轉影片，那我們的競爭對手是 Runway、Sora、可靈這些影片模型公司 —— 那我們一定輸，因為那是拚模型能力、拚 GPU 資本的戰場。
>
> 但**領養廣告**這個場景有三個特性，讓「純生成式影片」其實是**錯的解法**：
>
> **第一，內容不能是假的。** 這支影片的目的是促成領養。如果影片裡的貓是 AI 幻想出來的、毛色跟本尊不一樣，民眾到收容所看到本尊會有落差 —— 這是信任問題，嚴重的話是消保問題。所以我們的設計是：**Pet Profile（寵物檔案）是唯一事實來源**，腳本裡每一句話都要能對回 Profile。
>
> **第二，必要的照護限制不能被藏起來。** 例如「需長期服用腎臟處方飼料」「不可與其他貓同住」。一個純廣告導向的生成模型，為了讓文案更吸引人，天生傾向把這些略過 —— 而這正是**領養失敗、二次棄養**的主因。所以我們有獨立的檢查機制，強制檢查這些限制有沒有出現在腳本裡。
>
> **第三，真實素材本來就存在。** 收容所有寵物的實拍照片和影片。用 AI 生成一隻假的貓去取代一隻真的貓的實拍畫面，在這個場景是**負價值**。
>
> 所以我們的定位是：**以寵物真實資料治理為核心的短影音生產平台。**
> 流程是：資料整理 → 個性分析 → 腳本 → 分鏡 → 影音生成 → 審核 → 發布 → 成效回饋。
>
> **競爭力來自資料治理、人格化敘事、可控分鏡、人工審核、領養成效閉環 —— 不是單一影片模型。**
> 模型是可替換的零件，流程和治理才是資產。這句話是整個架構的核心。」

**素材組成的目標比例（刻意設計，不是能力不足）：**

| 來源 | 比例 |
|---|---|
| 真實影片剪輯 | 60% |
| 照片動態化（Ken Burns／Image-to-Video） | 20% |
| 字幕與貼圖 | 10% |
| AI 生成場景（須標示「部分畫面由 AI 創意生成」） | 10% |

## 【★】二、技術架構：九層 + 基礎設施（4 分鐘）

> 「系統分成九層，我快速帶過，然後聚焦在三個關鍵設計決策。」

| 層 | 做什麼 |
|---|---|
| 1. 資料處理層 | 上傳、素材品質檢查、寵物辨識與特徵抽取、Identity Card 生成、最佳片段選取 |
| 2. 內容策劃層（多代理） | Profile／Media Analyst／Persona／Marketing／Script／Storyboard／Fact-check 七個 Agent |
| 3. 生成式 AI 層 | 圖像生成增強、鏡頭級影片生成（I2V／T2V）、TTS 旁白、音樂音效 |
| 4. 影音製作層 | FFmpeg 剪輯、字幕貼圖特效、音訊混合、多尺寸輸出 |
| 5. 品質與安全審查層 | 寵物一致性、事實正確性、影音品質、內容合規（加權評分） |
| 6. 人工審核層 | 三欄式介面：Profile／影片預覽／分鏡＋QA，可單鏡頭重生、核准或退回 |
| 7. 發布與輸出 | 成品影片、封面圖、社群文案、字幕檔、生成紀錄 |
| 8. 社群平台發布 | TikTok、IG、Shorts、LINE、FB、領養平台 |
| 9. 成效追蹤與優化 | 全漏斗：曝光 → 3 秒停留 → 完播 → 點擊 → 諮詢 → 申請 → 會面 → **領養** |

> 「基礎設施是 Auth/RBAC、任務佇列、任務狀態機、PostgreSQL、物件儲存、Redis、監控。
>
> **請注意第 9 層的漏斗終點是「領養」，不是「觀看數」。** 這是我們跟一般行銷影片工具最大的差異，也是我後面想跟您討論 KPI 的地方。」

### 三個關鍵設計決策（重點講這裡）

**決策一：鏡頭級生成，不做一鏡到底**

> 「每支 30 秒影片拆成 **5–7 個 3–6 秒的鏡頭**，每個鏡頭是**獨立的 Job、獨立生成、獨立 QA**。
>
> 為什麼？三個理由：
> 1. **失敗只重生失敗的鏡頭，不整支重跑。** 我們實測一顆 AI 動態化鏡頭要 8 分鐘；一支影片如果在第 5 顆鏡頭掛掉，整支重跑等於浪費 40 分鐘。現在我們可以**續跑**，沿用已完成的鏡頭。
> 2. **人工審核可以退回單一鏡頭。** 審核員說「第 3 顆鏡頭的字幕不對」，我們只改那一顆，其他不動。
> 3. **可控性。** 一鏡到底的生成模型你無法局部修改，只能重新擲骰子。」

**決策二：腳本一次產出三種風格，不直接發布單一版本**

> 「同一隻寵物，同時產出**萌系、溫暖故事、反差幽默**三個版本的腳本，給人挑。
> 因為「哪種調性有效」是**經驗問題不是模型問題** —— 而且不同寵物、不同平台的答案不一樣。這也是後續 A/B 測試的基礎。」

**決策三：人工審核是必經關卡，不可跳過自動發布**

> 「這是硬性規範。搭配 QA 加權評分：」

| 檢查項 | 權重 |
|---|---|
| Identity Consistency（是不是同一隻寵物） | 30% |
| Factual Correctness（事實正確） | 25% |
| Visual Quality | 15% |
| Audio & Subtitle | 10% |
| Emotional Appeal | 10% |
| Platform Compliance | 10% |

> 「**低於 80 分不進人工發布畫面。而且事實正確性或合規檢查任一項失敗，無論總分多高都不可發布。**
> 也就是說，事實正確是**一票否決**，不是加權平均可以稀釋掉的東西。」

**另外兩個小但重要的決策：**
- **字幕與文字元件一律由後製引擎疊加**，不讓生成模型在畫面內直接畫字 —— 因為生成模型畫中文字會出現錯字和字型變形，這是已知且無解的問題。
- **每支影片都保留完整生成紀錄**：用了哪個 provider、什麼 prompt、哪些素材、審核結果，供事後追溯與合規查核。

## 【★】三、Provider Adapter：商用 API 與開源模型並列（2 分鐘）

> 「這是架構上我最想強調的一點，因為它直接關係到**成本、資安、跟廠商議價能力**。
>
> **所有 AI 呼叫都必須經過一個統一的 Provider Adapter 介面。業務程式碼裡禁止出現任何特定廠商的 SDK。**
>
> 這帶來三件事：
> 1. **不被廠商綁架。** 換掉 ElevenLabs 改成自架 TTS，是新增一個檔案 + 改一行設定，呼叫端程式碼一行都不用動。
> 2. **資安可控。** 涉及真實寵物臉部或收容所個資的資料，**預設走本地開源模型**，不出機房。只有明確標記可外送的資料才會呼叫商用 API；不確定時一律視為不可外送。
> 3. **成本可控。** 未來 Router 依序評估四個條件：**內容敏感度 → 時效性 → 成本上限 → Fallback**。急件走商用 API、批次走開源排隊、超過成本上限自動降級、商用失敗自動切開源重試。」

| 功能 | 商用 API | 開源方案 |
|---|---|---|
| LLM（腳本／QA 判斷） | Claude / GPT-4o | Llama 3.x、**Qwen2.5**、Mistral |
| VLM（素材檢查） | GPT-4V / Claude Vision | Qwen2-VL、LLaVA-NeXT |
| 影片 I2V／T2V | Runway、Veo、Kling、Luma | SVD、CogVideoX、**Wan2.2**、Open-Sora |
| TTS 旁白 | ElevenLabs、Azure TTS | **XTTS-v2**、F5-TTS、GPT-SoVITS |
| 內容審核 | OpenAI Moderation | LlamaGuard 3 |
| 音樂 | Suno / Udio | MusicGen |

> 「**目前的實作全部走開源、全部自架，跑在本機一張 RTX 5070 Ti 上，外部 API 成本是零。**
> 這是刻意的：先證明開源方案跑得動，商用 API 就變成「加速選項」而不是「必要成本」。」

## 【★】四、目前實作到哪裡：誠實的進度（3 分鐘）

> 「我想很明確地說明**哪些做完了、哪些刻意還沒做**，避免後面的期待落差。
> 目前在 **MVP 階段，已完成第三個切片**。」

### 已完成

**切片一 — 資料層**
- PostgreSQL + SQLAlchemy ORM，寵物檔案與生成紀錄都進資料庫
- Schema 演進走 **Alembic migration**（目前 4 份），有測試自動擋下「改了 model 卻忘記寫 migration」
- 管理 CLI：`init-db`／`import-profile`／`list-pets`／`show-pet`

**切片二 — 分鏡編輯與單鏡頭重生**
- 每次生成都有**獨立的輸出資料夾**，版本之間不互相覆蓋
- 單鏡頭重生**不重跑 LLM**，只 patch 指定鏡頭後重新渲染
- **每次重生都是新的一筆紀錄，不覆蓋舊的** —— 原始輸出與紀錄全數保留供追溯

**切片三 — Image-to-Video ＋ Web 介面**
- 三個 I2V provider 可用名稱切換：`svd`／`cogvideox`／`wan`
- FastAPI 後端 + 網頁前端，生成改成**背景執行**：立刻回 202 + task_id，前端輪詢進度條（腳本 1/3 → TTS → 鏡頭 n/m → 合併），關掉視窗或重整頁面都能接回還在跑的工作
- **給非工程使用者的中文表單 UI**：不用寫 JSON，勾選健康狀態、chip 編輯個性標籤、照片影片用檔案對話框上傳
- **鏡頭級 Job 紀錄 + 續跑**：`python -m pipeline.resume <job_id>`，沿用已完成鏡頭只補跑沒做完的
- **崩潰自癒**：webapp 啟動時會把上個 process 死掉留在 running 的 job 收成 failed，UI 不會永遠卡在「生成中」

### Image-to-Video 的實測選型（這段是重點）

> 「Wan2.2 這個 provider，我試了四條路才找到可行的那條。我想說明一下，因為它示範了**技術選型應該用實測數字決定**：」

| 方案 | 實測結果 | 結論 |
|---|---|---|
| diffusers + Wan I2V-A14B | 檢查點約 **118GB**，載入第 2 個元件時直接 SIGSEGV（機器 64GB RAM） | ❌ 裝不下 |
| diffusers + TI2V-5B | diffusers 對這個檢查點**沒有 I2V 支援**（官方已知 bug #13258） | ❌ 功能不存在 |
| Wan 官方 generate.py | 可用，但只有未量化 bf16，實測 **約 500 秒／step**，50 步等於**一顆鏡頭 7 小時** | ❌ 太慢 |
| **ComfyUI + FP8 量化 TI2V-5B** | **約 25 秒／step**，20 步 → **一顆鏡頭約 8 分鐘**，VRAM 約 **11GB** | ✅ **採用** |

> 「同一張卡、同一個模型，**FP8 量化 + ComfyUI 的記憶體管理讓速度快了約 20 倍**。
>
> 另外三個 I2V provider 的定位也不同：
> - **SVD-XT**：已在本機用實際寵物照片跑過手動驗證，確實會動 —— 但 **SVD 沒有文字條件，prompt 對它是無效的**，動的多半是鏡頭和背景，不是主體。
> - **CogVideoX-5B**：介面已實作，但 5B 在 16GB VRAM 上吃緊，還沒實機驗證。
> - **Wan2.2**：**文字 prompt 真的能指揮主體動作**（例如「貓輕輕搖尾巴、抬頭看鏡頭」），是目前品質與速度最平衡的選擇，而且是 **Apache 2.0 授權，商用無虞**。」

### 事實檢查機制的實測（誠實面對限制）

> 「這一點我想誠實報告，因為它是目前**最大的技術債**。
>
> 目前的照護限制檢查是**字串比對，不是語意理解**。我用真實 LLM 跑過驗證：
> - ✅ 成功攔截：某個風格的腳本**整個漏掉**了「不與其他貓咪同住」這個限制
> - ❌ 誤報：限制寫成完整句子「需要長期服用腎臟處方飼料，不可中斷」時，另一個風格用「需長期服用腎臟處方飼料」揭露了 —— 意思有到，但字串對不上，被誤判為缺漏
>
> **結論與現行對策：** 短的、關鍵字型的限制能可靠攔截；完整句子型的限制在模型改寫後容易誤報。所以目前的操作規範是**把 Profile 的限制欄位寫成短關鍵字**，並且把檢查結果當作「這裡要人看一下」，而不是「通過／不通過」的判定。
>
> **真正的語意事實檢查 Agent 是還沒還的債，我認為是下一個優先項。**」

### 安全性規範（若主管關心資安）

- API 金鑰、資料庫連線字串一律走 `.env`，**程式碼中禁止硬編碼**
- **禁止字串拼接組 SQL** —— 一律參數化查詢或 ORM
- **禁止字串拼接組 shell 指令** —— 呼叫 ffmpeg 的參數一律用 list 傳給 subprocess，`shell=False`
- 所有外部輸入（上傳檔案、Pet Profile、審核介面填寫的文字）都要經過 **pydantic schema 驗證**才進 pipeline
- 檔案上傳有**副檔名白名單、檔名淨化、同名不覆蓋、路徑包含性檢查**（防止任意檔案讀寫）
- 日誌與錯誤訊息不得包含完整 API 金鑰或個資

## 六、風險與已知限制（1.5 分鐘，主動說）

> 「我想主動把風險講清楚：」

1. **事實檢查目前是字串比對，不是語意理解** —— 已知會誤報，靠人工審核兜底。最需要補的一塊。
2. **一次只能跑一個生成任務** —— 生成會吃滿 GPU，第二個請求直接回 409。要支援多使用者並行需要真正的佇列和多張卡。
3. **Image-to-Video 一顆鏡頭 8 分鐘** —— 一支影片若 3 顆鏡頭要動態化就是 24 分鐘。這決定了產能上限。
4. **前端是無建置流程的純 HTML/JS**，不是架構文件最終目標的 React/Next.js —— 夠用，但要長期維護和多人協作時需要重寫。
5. **QA 加權評分目前只實作了結構性檢查**（鏡頭數、時間軸有無斷層重疊、字幕是否為空），**寵物一致性的 VLM 檢查還沒做** —— 那是權重最高的 30%。
6. **所有東西跑在單一台開發機上**，沒有部署、沒有備援、沒有監控。

## 【★】八、想請教主管的問題

> 「最後有幾個問題想請教您，我分成四類：」

### A. 產品方向與定位

1. **這個系統的第一個真實使用者是誰？** 我們是要先找一間收容所深度合作、把流程跑順，還是做成多家收容所都能用的平台？這兩個方向對接下來的權限系統和多租戶架構影響很大。
2. **我們自己營運這個系統，還是交給收容所自己操作？** 如果是後者，人工審核介面的易用性優先度會大幅提高（目前已做中文表單化，但還不夠）。
3. **競品或現有替代方案是什麼？** 收容所現在怎麼做宣傳影片 —— 志工手工剪？還是根本沒做？這決定我們的價值主張是「更快」還是「從無到有」。

### B. 成功指標與驗收

4. **這個專案的成功怎麼定義？** 我的設計是以**領養轉換率**為終點而不是觀看數。但領養是長週期、受很多影片以外因素影響的指標。您希望我們對外承諾哪一個？
5. **有沒有可接受的基準線？** 例如「一支影片從上傳到可發布，人工時間從 2 小時降到 15 分鐘」這類效率指標，是不是比轉換率更適合當第一階段的驗收？
6. **人工審核的通過率要到多少才算系統可用？** 10 支影片有 8 支審核員直接核准，跟只有 3 支，是完全不同的成熟度。

### C. 資源與技術決策

7. **GPU 資源的規劃是什麼？** 目前跑在一張 RTX 5070 Ti 上，一顆 AI 動態化鏡頭 8 分鐘、一次只能跑一個任務。要支撐真實產能，是**加卡**、**改用商用 API 付費換速度**、還是**接受目前產能先驗證價值**？我傾向第三個，但想確認您的看法。
8. **對外部 AI API 的成本上限是多少？** 目前全部開源自架、成本為零。如果有預算，我可以把 Router 做起來讓急件走商用 API —— 但我需要知道 cap 才能設計降級策略。
9. **這個專案有多少人力、多長時間？** 目前架構是為「一個人也能維護」設計的（同步流程、沒有 Celery、純 HTML 前端）。如果會有 3 人以上一起做，我應該現在就把佇列和前端框架補上，晚做成本更高。

### D. 合規與風險

10. **AI 生成內容的揭露義務，法務有沒有意見？** 我目前的設計是「AI 幻想場景必須標示『部分畫面由 AI 創意生成』」。這個標示的措辭和呈現方式需不需要走法務確認？
11. **寵物照片和收容所資料的外送政策，誰來核定？** 我目前的預設是「涉及真實寵物臉部或個資的資料一律走本地開源模型，不確定時視為不可外送」。這是我從技術端設的保守預設，但**這應該是政策決定不是技術決定**，想請您確認或指定核定的人。
12. **如果一支影片通過審核發布了，事後發現健康資訊有誤，責任流程是什麼？** 我在系統裡保留完整生成紀錄（用了哪些素材、哪個 provider、什麼 prompt、誰核准的）就是為了這個場景，但**下架和通知的流程**需要組織層面定義。

## 附錄：可能被追問的問題與備答

**Q：為什麼不直接用 Sora／可靈這種現成的影片生成服務就好？**
> 「可以用，而且我們的架構隨時可以接進來 —— 它就是 Provider Adapter 表格裡的一格。但它解決的是『畫面怎麼來』，只佔整個流程的一環。它不會幫我們檢查腳本有沒有漏掉照護限制、不會保留生成紀錄供合規查核、不會讓審核員退回單一鏡頭。**我們的價值在流程和治理，不在畫面生成本身。**」

**Q：現在做出來的影片品質，能直接發布嗎？**
> 「以真實素材剪輯 + 照片動態化的預設路徑，品質是可以的 —— 因為畫面本來就是實拍。**AI 動態化的鏡頭品質參差**，這也正是為什麼架構上人工審核是必經關卡、真實素材優先、AI 只補位。我不會說現在能無人值守自動發布，也不建議往那個方向做。」

**Q：這些是你自己寫的還是 AI 生成的？**
> 「開發過程有用 AI 輔助，但**架構決策、技術選型和踩過的坑都是實測驗證的**。剛才那張 Wan2.2 的四種方案比較表，每一行都是實際跑到失敗或跑出數字才淘汰的 —— 118GB 裝不下是實際 SIGSEGV，500 秒一步是實際測出來的。」

**Q：多久可以上線？**
> 「取決於『上線』的定義。**內部試用**：現在就可以，介面已做到非工程人員能操作。**給一間收容所實際使用**：建議先補上語意版事實檢查和寵物一致性檢查，因為那是對外發布的風險守門。**多家收容所的平台**：需要權限系統、任務佇列、部署環境，那是另一個量級。我想先確認方向再估時程。」

**Q：如果換人接手，接得起來嗎？**
> 「架構文件、開發規範、啟動手冊都有。**98 個測試是規格的可執行版本** —— 改壞了會有測試擋。Provider Adapter 的設計也是為了讓換模型不用讀懂整個 pipeline。我覺得風險可控，但**單點依賴確實存在**，這也是我問人力規劃那題的原因。」
