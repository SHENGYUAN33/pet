# 口稿・濃縮版（約 5 分鐘）

> 完整版在 [presentation_script.md](presentation_script.md)。
> 這版是走廊上、電梯裡、或主管只給你五分鐘的時候用的。

---

主管好，跟您快速報告我做的系統。

**一句話：幫收容所自動做寵物領養的短影片。**

收容所要幫一隻狗找認養人，得有人拍照、寫文案、剪影片，一支弄下來要兩三個小時，而大部分收容所根本沒這個人力。

我做的是：**把寵物的照片、影片、基本資料和健康紀錄丟進來，系統自動產出一支三十秒的直式短影片，有旁白、字幕、配樂，人審核過就能直接發到 IG、TikTok。** 旁白是用寵物第一人稱講的，像牠自己在自我介紹，比較容易讓人有情感連結。

---

## 我刻意沒有做成「AI 文字生影片」，這是整個設計的核心

市面上很多工具是打一段文字就生一支影片。**我沒有走那條路，有三個原因。**

**第一，影片裡不能有假的東西。** 這是要讓人真的把動物帶回家，不是廣告。如果影片裡的貓是 AI 想像的、毛色跟本尊不一樣，民眾到現場會有落差，那是信任問題。所以我的設計是**寵物的真實資料是唯一事實來源**，影片裡每句話都要能對回牠的資料。

**第二，該講的限制不能被藏起來。** 比如「要一輩子吃腎臟處方飼料」「不能跟其他貓住」。這些講出來領養意願會降，所以 AI 天生傾向略過。但**領養後又被退養，最大原因就是事前不知道要付出什麼**。所以我做了一道檢查，確認這些限制有沒有真的出現在旁白和字幕裡。

**第三，真實素材本來就有。** 收容所有實拍照片。用 AI 生一隻假的貓取代真的貓，在這個場景是扣分不是加分。

**所以我的定位是：這不是 AI 影片生成工具，是一套以真實資料為核心的影片生產流程。**

AI 模型只是裡面隨時可以抽換的零件，價值在整條流程 —— 資料怎麼管、內容怎麼確保是真的、人怎麼審。

## 系統怎麼運作

流程是：資料進來 → AI 寫腳本 → 語音合成配音 → 一顆一顆鏡頭做出來再接起來 → 自動檢查 → **人工審核**（強制，不能跳過）→ 發布。

架構長這樣：

```
┌────────────────────────────────────────────────┐
│  網頁介面（FastAPI ＋ 純 HTML）                   │
│  新增寵物／上傳素材／按下生成／看進度／人工審核      │
└────────────────────────────────────────────────┘
                        │
┌────────────────────────────────────────────────┐
│  主流程（我自己寫的 Python）                       │
│  寫腳本 → 分鏡 → 配音 → 逐顆鏡頭渲染 → 合併 → 檢查  │
└────────────────────────────────────────────────┘
          │                              │
┌───────────────────────┐   ┌────────────────────────┐
│  Provider Adapter     │   │  FFmpeg（影片組裝）       │
│  統一介面（唯一對外層）  │   │  字幕燒錄／串接／混音      │
└───────────────────────┘   └────────────────────────┘
          │
          ├─ LLM 寫腳本   → Ollama ＋ Qwen2.5      〔本機〕
          ├─ TTS 配音     → XTTS-v2                〔本機〕
          ├─ 照片動起來    → SVD ───────── diffusers 〔本機〕
          │                CogVideoX ─── diffusers 〔本機〕
          │                Wan2.2 ────── ComfyUI ──┐
          └─ 背景生成     → SDXL ─────── ComfyUI ──┤
                                                   │
                              獨立的 ComfyUI 伺服器 ←┘
                              （不在專案裡，透過網路呼叫）

  資料層：PostgreSQL（寵物檔案／生成紀錄／每顆鏡頭的紀錄）
  檔案層：素材與輸出影片放檔案系統，不塞進資料庫
```

**這張圖我想指出三件事：**

**所有 AI 都被關在「Provider Adapter」這層後面**，主流程從頭到尾不知道自己在用哪個廠商的東西，所以換模型不用動主流程。

**影片組裝走 FFmpeg，跟 AI 那條線是分開的** —— 也就是說**就算今天所有 AI 全部拿掉，用實拍影片加照片動態效果，這套系統一樣做得出影片。AI 是加值，不是命脈。**

**ComfyUI 在最右下角，是一顆葉子不是根。** 我另外兩個模型完全不經過它，一樣跑得出影片。

**幾個關鍵設計：**

**影片是一顆一顆鏡頭做的，不是一次生成整支。** 三十秒切成五到七顆鏡頭，各自獨立生成、獨立記錄。好處是**失敗不用整支重來** —— AI 動態化一顆鏡頭要八分鐘，跑到第五顆掛掉，整支重跑就白白浪費四十分鐘。我做了續跑，已完成的鏡頭留著，只補沒做完的。而且審核的人可以只退回一顆鏡頭。

**腳本一次寫三種風格**（萌系、溫暖故事、反差幽默）給人挑。因為哪種有效是經驗問題不是技術問題，而且不同動物、不同平台答案還不一樣。

**所有 AI 呼叫都經過一層統一介面**，主流程裡不會出現任何特定廠商的東西。換模型只要多寫一個檔案、改一行設定。這帶來三件事：不被廠商綁死、**真實動物照片預設全在自己機器上處理不外流**、**現在全部用開源模型，對外 API 費用是零。**

**字幕是後製疊上去的**，不讓 AI 在畫面裡直接畫字 —— 因為 AI 畫中文一定會出錯字。

## 技術上我覺得最值得講的一件事

「讓照片動起來」這個功能，**我試了四種做法才找到能用的。**

前三種分別是：模型檔案一百一十八 GB，我機器裝不下；換小模型，結果那套工具根本沒支援「照片轉影片」；改用官方程式，功能對了但**實測一顆鏡頭要跑七個小時**。

第四種我改用 ComfyUI 搭配壓縮過的模型檔。**同一張顯卡、同一個模型，速度快了二十倍，一顆鏡頭八分鐘。** 這就是現在採用的方案。

**我想強調的是，這四種不是查資料查出來的，是一種一種實際裝下去跑，跑到爆掉或跑出數字才淘汰的。**

## 最近補的兩個功能，都是為了不浪費素材

**一個是結尾集錦。** 一支影片只放得下七張照片，但收容所可能傳了十三張。**願意傳十三張的人是希望十三張都被看到的。** 所以我在影片最後加一顆快切的集錦鏡頭，把沒用到的都放進去，故事節奏不變，每張照片都露出。

**一個是背景生成。** 橫的照片放進直式畫面上下會空兩條，我接了開源的圖像模型來補。這裡有個設計我想特別提 —— 我做了兩種模式：**「延伸」只生成空白處，照片拍到的東西一個像素都不動；「替換」是把寵物摳出來換整個場景，真動物、假地方。**

**所以只要用了「替換」，系統會自動在畫面燒上「部分畫面由 AI 創意生成」，強制的，使用者關不掉。**

我沒有讓標示變成一個選項 —— 因為只要是選項，就一定有人忘記、有人故意不加。

## 測試

**目前一百七十八個自動化測試，全部通過。** 測試程式碼三千八百行，功能程式碼五千兩百行，**差不多每四行功能配三行測試。**

規範是每個新功能、每個修掉的錯誤都要有測試。意義是**之後換人接手，改壞了測試會馬上告訴他。**

## 我主動講幾個目前的不足

**一，那個「照護限制有沒有被講出來」的檢查目前只是文字比對，不是真的理解語意。** 我實測過：有一次成功抓到腳本完全漏掉「不與其他貓同住」；但另一次限制寫得比較長，腳本用不同措辭講了同一件事，**意思有到但字對不上，被誤判成漏掉。** 目前是當作「這裡要請人看一下」，靠人工審核兜底。**真正能理解語意的查核，是我認為下一個最該補的。**

**二，品質評分裡權重最高的「影片裡的動物是不是本尊」，佔百分之三十，我還沒做**，那需要一個會看圖的 AI 模型。

**三，一次只能跑一個**，生成會吃滿顯卡。要多人同時用需要更多卡跟排隊機制。

**四，整套跑在我這台開發機上**，沒有正式部署、沒有備援、沒有監控。

還有一些是我**刻意先不做的** —— 素材自動檢查、音樂生成、社群自動發布、成效儀表板。**因為現在做等於在還沒確定有沒有人要用之前先花時間蓋房子。** 我寧可先把核心流程跑通、找真實收容所試用，再決定補哪些。

## 我建議接下來

最優先是把**語意版的事實查核**和**動物一致性檢查**補上，因為這兩個是影片發出去前的守門員，現在是缺的。

然後我很想**找一間收容所實際跑五到十隻真的動物**。到目前為止我都是用測試資料驗證，我需要真實場域的回饋 —— 真正的收容所照片是什麼品質、志工卡在哪、做出來的影片他們敢不敢發。**這件事我覺得比再多寫功能都有價值。**

## 幾個想請教您的問題

1. **我們的第一個真實使用者是誰？** 是先找一間收容所深度合作，還是要做成很多家都能用的平台？這兩條路對架構影響差很多。

2. **這個專案的成功怎麼定義？** 我的設計是以「真的有沒有被領養」為終點，不是看播放數。但領養週期長、受很多影片以外的因素影響。您希望我們對外承諾哪一個？還是第一階段先用效率指標，比如「一支影片的人工時間從兩小時降到十五分鐘」？

3. **顯卡資源您怎麼想？** 現在一張卡、一次跑一個。要撐真實產能是加卡、花錢買商用服務、還是接受現在的產能先驗證價值？**我自己傾向最後一個**，想聽您的看法。

4. **這個專案會有幾個人？** 我現在的架構是照「一個人也能維護」設計的。**如果之後會有三個人以上，有些基礎建設我應該現在就補，晚做成本高很多。**

5. **動物照片能不能送到外部服務，這個誰決定？** 我現在的預設是「涉及真實動物臉部或個資的一律留在自己機器上」。**但我覺得這是政策決定，不該由我這個做技術的自己定**，想請您確認或指定該負責的人。
